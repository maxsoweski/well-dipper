**Astra review of the planet-name mismatch (2026-09-30)** — `.astra/jobs/20260930-091550-planet-name-mismatch-review/report.md`
(runner exit 4 = Astra could not write in its read-only sandbox; the analysis is complete). Claims checked against the code:
1. Flight names planets from a WARP COUNTER, not the star: `src/main.js:7567` `seed = system-${seedCounter}` feeds
   `generateSystemNames` (:7596); the counter bumps per warp (:6644). The Nth system visited gets the same invented words
   whichever star it is; a revisit renames. Main cause of the repeats. CONFIRMED (and re-read by the coordinator).
2. Three independent namers disagree — legacy nav `<system>-N` (NavComputer.js:916-926), design nav
   `generatePlanetName(makeRng(star.seed+':names')…)` (navViewModes/state.js:627,657), flight (above). Flight's names live
   only on `system.names` (main.js:7949), never on `_systemData`, so the nav has nothing shared to read. CONFIRMED.
3. `TAU VELA-94`-style labels are SECTOR names (GalacticSectors.js:234; designs.js:2854), not system names. CONFIRMED.
4. Duplicates inside one system: the ~10% `<system> Minor|Outer|Far|Nova|Ultima` branch picks with no uniqueness
   (NameGenerator.js:527-530); same for the invented-word branch and moons. CONFIRMED by reading.
5. Cockpit TARGET/INFO panels drop leading words to fit (`fitDesignation`, cockpit/designation.js:46-56), so `… b` and
   `… Nova` show as bare `b` / `Nova`. CONFIRMED.
Proposed fix: one per-system names object attached to the system data, read by all three; procgen body names seeded
from the star, not the counter. Open for Max: whether generated planets keep invented names or become `<system> b`.
**ORDER (Max, 2026-09-30):** "Before implementing this fix we will need to address the other naming system issue I
mentioned" — the unique-but-meaningless system-name convention gets redesigned FIRST; the shared-names fix above waits on it.

**New defect, measured 2026-09-30 (system XIGMAG-2AE101G, IOTA AQUILA-6, near the core):** entering PRISM starts the
old background star loader (`_scheduleBgExpand`, NavComputer.js:3853, from `9182a7b`, 2026-03-24 — pre-dates the menu

`_queryYRange` → `findStarsInPrism` → `potentialDerivedDensity` → `_spiralPotentialOnly` (GalacticMap.js:843, 67 s of a
94 s trace). Frames on PRISM ran ~3.1 s each for ~30 frames until the slab reached ±3 kpc (63,924 stars). Queued keys
land all at once when a step ends, which is the "15 seconds". Likely far milder at Sol (09-21 measured 13 ms frames) —
density cost scales with location. Fix candidates: cache/precompute the density per hash cell, slice each step into
small budgets, or move the query to a worker.

**Naming input for the redesign (Max asked how Elite Dangerous does it):** Elite names procgen systems
`<sector name> <boxel code><mass letter><n>-<m>` (e.g. "Preia Phoe CZ-C c14-89"): a pronounceable sector name built from
syllables, then a code giving the cube and star index. Real stars keep catalogue names. Contrast with ours
(docs/NAMING_AND_REAL_OBJECTS.md §1): survey designation `PVX J4K7Q2M+9XP3RWZ` or multi-part fantasy, both injective in the
position locator, with NO shared readable part — our sector names (`TAU VELA-94`) never appear in a system's name. Same
gap as Max's stop-1 ask (the label should show which sector/region you're in).
Sources: https://forums.frontier.co.uk/threads/how-do-systems-get-their-names.555562/ · https://voxstellar.com/about

**NAMING + PRISM SEGMENTS — Max's direction (2026-10-02), verbatim:** "I like the Elite approach of having readable
syllabes at the beginning, and naming stars (outside of those that are real catalogues stars, in-universe fictional
systems etc) based on their galactic location. I'd like ours to work similarly. Which is something we'll need to adjust
at the prism level. We have few enough prisms that each is nameable; but they're very tall because of the system used to
create them from a top-down grid. So they'll need to be broken up into segments somehow, and this will enable us to
meaningfully navigate their vertical height in the nav system--right now you can just press R and F or drag the vertical
slider but it takes minutes to go from one section to another. If we built a segmentation system, you could see the
un-highlighted segments in the nav bar and click or drag to a new one quickly, or use existing R and F controls to slowly
pan up or down"
→ To scope with `dev-collab-scope` after the walk; precedes the planet-name fix. Connection: the PRISM stall above loads
the whole ±3 kpc column in 0.1 kpc steps — loading per segment would bound that work by design.

**Max asked (prism count):** "When I look at the galaxy screen, I see fewer than eight by eight cells in that grid. Each one
of those cells is a sector, no?" → NO, and the screen gives no way to know it. The GALAXY grid is the 4 kpc BASE grid of
`GalacticSectors` (8×8, `baseGridSize = 4.0`, galaxyR 15 → nBase 8; empty corner cells skipped, GalacticSectors.js:97-121).
Sectors are that grid SUBDIVIDED by density (quadtree, up to 4 halvings: 4 → 2 → 1 → 0.5 → 0.25 kpc, :136) into 775
sectors that appear only in the right-hand list, never drawn on the map. Sol's 4 kpc square holds 16 one-kpc sectors;
a core square up to 256. Two different divisions share one screen with nothing relating them — a navigation defect in
its own right, and the root of stop 1's "I'm not actually sure what these are telling me."

**GOVERNING RULE (Max, 2026-10-02), verbatim:** "this is not just a navigation defect, this is a major problem that never
surfaced until now. So, at each level of the navigation screen, what should be represented by the cells in the grid is
the next level down in terms of resolution. So, each cell in the galaxy should represent a single sector. Otherwise, we
won't be able to actually navigate between them coherently. Every cell in the sector view should be displaying a single
region. Every cell in the region view should be displaying a single prism. If that's not how it's working today, we need
to reconsider the scale at which each of these things is representing what's inside of it. And consider a different
approach if that's not feasible."
→ Today NONE of the three levels obey it: GALAXY draws the 4 kpc base grid (not the 775 adaptive sectors); SECTOR and
REGION draw view-relative 8×8 / 16×16 tiles (NavComputer.js:4651-4657, designs.js:576-581), not fixed regions/prisms.
Sent to a plan-revision agent.

**CORRECTION (plan-revision agent, checked by coordinator at designs.js:760-767, :1062-1066):** the GALAXY grid is NOT the
4 kpc base grid — it is a plain 8×8 grid of ~4.5 kpc cells re-fitted to the visible disc. Of its 52 drawn cells none holds
exactly one sector (each touches 2–163, median 4; Sol's touches 15). Clicking resolves to the irregular sector under the
pointer, which the code itself calls "DIFFERENT OBJECTS". Sol's 4 kpc base square holds 10 sectors (not 16); the busiest 223
(not 256). Conclusion unchanged: no screen obeys one-cell-one-child today.
